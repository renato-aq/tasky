# Code Review

Data: 2026-04-02

## Findings

### P1: Cross-project tasks can be added to a sprint without validation

Arquivo: `src/TaskTracker.Application/Features/Sprints/Commands/AddTasksToSprint/AddTasksToSprintCommandHandler.cs`

The handler assigns every `TaskId` to the target sprint but does not verify that each task belongs to the same project as the sprint. That permits invalid project/sprint links and can effectively move tasks out of their real project backlog.

### P1: Task creation allows attaching a task to a sprint from another project

Arquivo: `src/TaskTracker.Application/Features/Tasks/Commands/CreateTask/CreateTaskCommandHandler.cs`

When `SprintId` is provided, the code does not load the sprint or confirm it belongs to `command.ProjectId`, so a task can be created under project A and immediately linked to a sprint in project B.

### P2: Soft-deleted projects are still mutable through write-side lookups

Arquivo: `src/TaskTracker.Infrastructure/Persistence/Repositories/ProjectRepository.cs`

`FindAsync` appears to return deleted rows, while the read side filters them out, so command handlers can still update or delete projects that should already behave as gone.

### P2: Nested subtask mutation routes do not enforce the parent task

Arquivo: `src/TaskTracker.Api/Controllers/TasksController.cs`

The routes accept both `taskId` and `subTaskId`, but only `subTaskId` reaches the application layer, so clients can mutate or delete a subtask through the wrong parent task URL.

## Residual risk

I have not re-verified the implementation beyond the reported issues, so there may also be missing tests around project/sprint integrity and nested subtask ownership.
